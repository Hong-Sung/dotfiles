# 공통 AI 작업 규칙 (Claude · Codex · Antigravity)

모든 프로젝트에 적용한다. 프로젝트 규칙은 각 저장소의 `AGENTS.md`에 있고, 둘이 충돌하면 프로젝트 규칙을 따른다.
이 파일이 원본이다: `~/.config/ai/AGENTS.md`

## 1. 코딩 원칙
- **먼저 생각하기**: 가정을 드러내라. 해석이 여러 개면 조용히 하나를 고르지 말고 제시한다. 불확실하면 묻는다. 더 단순한 방법이 있으면 말한다.
- **단순하게**: 요청하지 않은 기능, 설정 옵션, 한 번만 쓰는 추상화를 만들지 않는다. 불가능한 상황을 위한 에러 처리를 넣지 않는다.
- **필요한 곳만 고치기**: 바뀐 모든 줄은 요청과 직접 연결돼야 한다. 내 변경 때문에 안 쓰게 된 것만 지우고, 무관한 죽은 코드는 알려만 준다.
- **목표 기반 실행**: 검증 가능한 완료 기준을 정하고, 여러 단계 작업은 짧은 계획과 확인 방법을 먼저 밝힌다. 빌드 통과는 완료가 아니다. 핵심 시나리오까지 확인한다.
- **사용자가 보는 화면에서 확인하기**: 완료라고 말하기 전에 사용자가 실제로 볼 대상(UI, Foxglove, 브라우저 등)에서 확인한다. 내가 조회하기 편한 내부 계층만 보고 끝내지 않는다. 시뮬레이션이나 실험을 반복하기 전에는 무엇을 보고 판단할지 먼저 정한다.

## 2. Git
- **커밋과 push는 사용자가 명시적으로 지시할 때만 한다** ("commit", "커밋해", "push").
  - 작업 방향에 대한 승인("그래", "진행해", 선택지 답변)은 커밋 지시가 아니다.
  - 한 번 받은 커밋 승인은 다음 변경 묶음으로 이어지지 않는다.
- 커밋 지시를 받았는데 관련 빌드와 테스트가 이미 통과했다면, 전체 테스트를 다시 돌리느라 커밋을 막지 않는다.
- 브랜치 머지는 `git merge --no-ff`를 쓴다. squash는 쓰지 않는다.
- 머지한 브랜치는 머지 직후 지운다(`git branch -d`).
- 큰 변경은 새 브랜치에서 작업하자고 먼저 제안한다.

## 3. 소통
- 한국어로 답한다. 기술 용어와 코드 식별자는 원문 그대로 쓴다.
- 결론부터 간결하게 말한다. 서론을 붙이지 않고, 이미 말한 내용이나 완료 요약을 반복하지 않는다.
- 웹 검색과 페이지 조회는 묻지 않고 진행한다.

## 4. 작업 연속성 (도구 간 인수인계)
세 도구를 번갈아 쓰므로, 상태는 각 도구의 메모리가 아니라 **저장소 안의 파일**에 남긴다.
- **작업 시작 시**: 저장소의 `docs/handoff.md`를 먼저 읽고, `git log`와 `git status`로 대조한다.
  - 파일이 없거나 오래됐을 때만 다른 도구의 세션 로그를 참고한다(Claude는 `~/.claude/projects/`, Codex는 `~/.codex/sessions/`). 로그는 크니 최근 부분만 본다.
- **작업 단위를 마칠 때**(기능 완료, 커밋 직전, 중단, 도구 전환): `docs/handoff.md`를 갱신한다. 파일이 없으면 아래 형식으로 만든다.
- **결정과 규칙**: 사용자가 정한 설계 결정("~하기로 했다")이나 작업 규칙은 도구 메모리에만 두지 않는다. 프로젝트의 `AGENTS.md`(규칙)나 `docs/`(설계 결정)에 적는다.

`docs/handoff.md` 형식(짧게 유지하고, 끝난 항목은 지운다):
```markdown
# Handoff
갱신: YYYY-MM-DD HH:MM · 도구명 · 브랜치 / 마지막 커밋

## 지금 하는 일
## 상태 (완료 / 검증 결과)
## 다음 할 일
## 미해결 · 주의
## 관련 문서
```
